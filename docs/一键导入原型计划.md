# ICTHub 一键导入原型计划

## 1. 目标

先打通一条可以部署验证的通用材料导入链路：实验室成员可以填写项目简介、粘贴多个链接，并混合上传源码、压缩包、文档、PPT、视频、图片等附件。后端在隔离目录中安全归一化和解包，生成项目草稿并交给成员确认。

首期不调用真实模型、不自动创建 GitHub 仓库。Codex 与 GitHub 发布器作为后续可替换阶段接入，避免在上传链路尚未稳定时暴露 API Key 或组织凭据。

Codex 使用已 Fork 的仓库：<https://github.com/winbeau/codex>。集成方式固定为独立 app-server/worker，不把 Codex 内部 Rust crate 直接链接进 Axum 主进程。

## 2. 泛化输入模型

所有来源统一抽象为 `import_inputs`：

- `input_kind=file`：ZIP、PPTX、PDF、DOCX、视频、图片、源码包等。
- `input_kind=link`：GitHub、百度网盘及普通网页链接。
- `input_kind=prompt`：成员提供的项目简介和整理要求，后续直接作为 Codex 提示上下文。
- `provider`：`upload`、`github`、`baidu`、`web`，后续可扩展。
- 一个 `import_job` 可以关联多个输入，因此 ZIP、GitHub 链接和补充文件能够进入同一分析任务。

原型已支持一个任务上传多个直接附件和 ZIP。混合输入会先在任务隔离目录中归一化，再进入同一安全索引流程。附加链接会保存为 `pending_parser`，不会被下载或访问；这为 GitHub clone 和网盘下载保留了稳定接口。

## 3. 原型处理流程

1. 成员填写简介、批量粘贴链接，并拖入一个或多个附件；三类输入至少提供一类。
2. 后端将输入写入每任务独立的隔离目录。
3. 检查压缩路径、符号链接、文件数量、单文件大小和总解压体积。
4. 跳过 `.git`、`node_modules`、`target`、虚拟环境等生成目录。
5. 对文件建立分类索引，读取有限的 README 和配置文本作为规则回退语料。
6. 确定性回退生成项目名、slug、简介和五类主分类，并提取简介中明确写出的正式标签与责任信息。
7. 前端轮询任务状态，展示项目草稿、文件分类、封面候选和风险提示。
8. 成员可将草稿带入现有“上传项目”表单继续确认。

草稿采用谨慎填充规则：项目名、简介、主分类和资源可以根据材料推断；标签、负责人、来源和奖项只有在成员简介中以明确字段写出时才填入，例如 `标签：Web、校园服务`、`负责人：张三`。技术栈命中不会自动转成标签，来源文件名也不会自动成为项目来源。

前端提供 Codex 工作流程弹窗，展示输入收集、安全整理、材料理解、草稿生成和人工确认五个阶段。任务启动后自动打开，成员也可以随时手动查看当前阶段。

## 4. 数据与 API

SQLite 新增：

- `import_jobs`：任务状态、阶段、进度、分析器、结果和错误。
- `import_inputs`：提示、文件、链接来源、提供方、摘要、哈希和处理状态。
- `import_artifacts`：解包后的文件路径、类别、MIME、大小、解析器和封面候选。

API：

- `POST /api/v1/import-jobs`：multipart 上传；可重复使用 `file` 字段提交多个附件，`links` 为 JSON 数组，`prompt` 为项目简介。
- `GET /api/v1/import-jobs/{id}`：读取任务进度和解析结果。
- `POST /api/v1/import-jobs/{id}/cancel`：任务进行中可取消，保留已上传材料和前端草稿。
- `POST /api/v1/import-jobs/{id}/refine`：整理完成后保存补充提示，作为后续 Codex refinement 输入。

两个接口都要求 Feiyue 登录且为实验室成员。上传任务异步执行，HTTP 请求不等待完整解包完成。

## 5. 安全边界

- 上传内容不得执行，禁止依赖安装、构建脚本和 Git hooks。
- Codex worker 使用只读工作区、禁用网络，并与 GitHub 发布器分进程运行。
- OpenAI API Key 只进入模型代理或受限 worker；GitHub Token 只进入可信发布器。
- 推送前增加密钥、个人信息、超大文件和许可证检查。
- 删除来源 `.git` 时必须验证隔离工作目录的绝对路径。
- 生产环境限制并发任务数；4 核 8G 首期建议重型任务并发为 1。

## 6. 分阶段配置

### 阶段 A：通用附件原型

- 配置导入存储目录和体积限制。
- 部署并用真实 ZIP、PPT、文档和视频混合验证上传、轮询、归一化、解包、归类和草稿回填。

### 阶段 B：Codex 分析

- 确认 Codex app-server 固定版本及构建产物。
- 配置模型 Base URL。
- 通过服务器 secret 注入 API Token，不写入仓库或 SQLite。
- 定义严格 JSON Schema，并以确定性回退作为超时/失败降级。
- 接入 PPTX/DOCX/PDF 内容提取、视频关键帧和可选语音转录。

### 阶段 C：GitHub 来源

- 配置只读来源凭据。
- 浅克隆到隔离目录，默认不取 submodule、不运行 LFS smudge 和 hooks。
- 保存原 URL、commit SHA、许可证和授权备注。
- 删除隔离副本的 `.git` 后进入与 ZIP 相同的归类流程。

### 阶段 D：私有仓库发布

- 确认组织名和仓库编号规则。
- 配置最小权限 GitHub Token 或 GitHub App。
- 发布器负责原子分配编号、创建 private 仓库、初始化提交和推送。
- 增加幂等键和对账，处理“仓库成功、数据库失败”等部分成功情况。

### 阶段 E：链接解析与语义合并

- 下载或克隆 GitHub、网盘和普通网页来源，并与已支持的多附件输入进入同一任务。
- 根据 SHA-256、文件名和语义结果去重。
- 给每条结论保留来源证据，避免不同材料冲突时静默覆盖。

## 7. 原型验收标准

- 非成员不能创建或读取导入任务。
- 合法的单 ZIP、多附件、纯简介或纯链接输入均返回任务 ID，前端能看到阶段与进度。
- 路径穿越、符号链接、压缩炸弹和超限文件被拒绝。
- 源码、文档、PPT、视频、图片、数据和压缩文件能正确归类。
- 图片能成为封面候选。
- 未配置 Codex 时明确显示 `deterministic_fallback`，不伪装为 AI 结果。
- 工作流程弹窗允许填写补充提示；完成后可保存给 Codex，整理过程中取消不会清空当前草稿。
- 附加 GitHub/网盘/网页链接保存在同一任务中并标记等待解析器。
- 草稿可以进入现有上传表单继续人工确认。
- 原型不读取任何 OpenAI 或 GitHub Token，也不改动 Feiyue。

## 8. 服务器首测顺序

1. 配置 `ICTHUB_IMPORT_ROOT`、上传限制和解压限制。
2. 部署数据库迁移与后端、前端构建。
3. 登录实验室成员账号，先上传真实 ZIP，再测试 ZIP + PPT + 文档 + 视频混合附件。
4. 检查任务目录权限、SQLite 记录、文件分类和草稿回填。
5. 验证失败 ZIP 不影响后端服务。
6. 链路稳定后，再逐项配置 Codex Base URL、API Token、GitHub 组织与 Token。
